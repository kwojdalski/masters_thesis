## Detailed diagnosis: why the H4 run is slow and its memory keeps climbing

### Where it happens

`src/trading_rl/trainers/training_loop.py`, inside `TrainingLoop.run()`, lines 71–77:

```python
with _profiler.stage("buffer_extend", 2):
    if trainer._use_replay_buffer:
        trainer.replay_buffer.extend(data)
        max_length = trainer.replay_buffer[:]["next", "step_count"].max()
        buffer_len = len(trainer.replay_buffer)
    else:
        max_length = data["next", "step_count"].max()
        buffer_len = data.numel()
```

This is the body of the **main collector loop** — it runs once per `data` batch pulled from `trainer.collector`, for the entire duration of training. It is not gated by any interval, sampling condition, or "first N steps" guard. It runs on batch 1 and it runs identically on batch 50,000.

### What `trainer.replay_buffer[:]` actually costs

`trainer.replay_buffer` (`base.py:383-388`) is a TorchRL `ReplayBuffer` backed by `LazyTensorStorage(config.buffer_size)`, with `buffer_size` defaulting to **100,000** transitions (`config.py:361`). `LazyTensorStorage` pre-allocates a single contiguous `TensorDict` sized for the whole storage capacity the first time data is written to it, so it behaves like a big pre-sized array from that point on.

`replay_buffer[:]` calls `ReplayBuffer.__getitem__(slice(None, None, None))`, which resolves to the storage's `get()` over the *entire filled range* of that array. Concretely, this:

1. Indexes/gathers every currently-populated row of the storage TensorDict (every field: observations, actions, rewards, `next` sub-TensorDict, `step_count`, `done`, `terminated`, everything the buffer was constructed with — not just the one field we actually want).
2. Materializes that into a **new TensorDict object** — a real allocation, not a lazy view, since TorchRL indexing on a `LazyTensorStorage` performs `index_select`/advanced indexing across all keys to build the returned batch.
3. Then we throw all of it away except `["next", "step_count"].max()` — a single scalar.

So every iteration pays for a full copy of the buffer's current contents (potentially every observation feature for up to 100,000 HFT LOB transitions, which for a wide microstructure feature vector is not small) purely to compute one number.

### Why this explains "takes ages"

The buffer starts near-empty and fills up to `buffer_size` as training proceeds. So the cost of this call is **O(current buffer occupancy)**, and it's paid on **every single collector batch**, not just occasionally. Integrated over a run, that's roughly:

```
total wasted work ≈ Σ (buffer occupancy at batch i)   for i = 1..num_batches
                   ≈ O(num_batches × buffer_size)      once the buffer is full
```

i.e. it degrades toward quadratic-ish behavior in the steady state rather than the O(1)-per-step cost you'd expect from an off-policy update loop. With H4 running **5 trials × 200,000 steps** (`scripts/run_h4_experiments.sh` defaults: `N_TRIALS=5`, `STEPS=200000`) against a TD3 scenario (`pooled/td3_hft_lob_state_space_pooled_streaming_selected_dsr`, which is off-policy and therefore uses the replay-buffer branch, not the PPO branch), this cost is paid across every trial, every batch, for the whole run.

The kicker: **the result is almost always discarded.** `max_length` is passed into `trainer._optimization_step(i, max_length, buffer_len)` and from there only ever reaches `_log_progress(...)`, which is gated by:

```python
# base.py:443-445
def _should_log_step(self, step: int) -> bool:
    return step % max(1, self.config.log_interval) == 0
```

with `log_interval = 1000` by default (`config.py:385`). So the value is used roughly **1 time in 1000** — the other 999 computations of it are pure waste. This checks out across `td3.py`, `ddpg.py`, and `sac.py`, all of which document `max_length` identically as "Maximum episode length in buffer" — a diagnostic-only value.

### Why this explains the "memory leak"

It isn't a leak in the strict sense (no Python object outlives its scope, nothing is unreachable). It's **allocator churn from large, monotonically-growing temporary allocations**:

- Every iteration allocates a fresh TensorDict roughly the size of "everything currently in the buffer." As the buffer fills toward 100k entries, these temporaries get larger and larger, batch after batch.
- If the buffer/tensors live on GPU, PyTorch's CUDA caching allocator does not return freed blocks to the driver — it holds them in its own free-block cache for reuse. A workload that keeps requesting ever-larger blocks (because the "live" size grows every call) fragments that cache: old smaller free blocks can't be reused for the new larger request, so the allocator keeps requesting more from the driver. `nvidia-smi` / process RSS then shows memory climbing over the course of the run and never coming back down — which reads exactly like a leak from the outside, even though every individual TensorDict is correctly freed by Python's refcounting once the statement ends.
- On CPU it's the analogous effect with `malloc`/glibc arena fragmentation from repeated large alloc/free cycles of varying-but-growing size.

This pattern — "temporary object recomputed from an ever-growing collection, every iteration, mostly unused" — is a textbook way to get exactly the two symptoms reported: wall-clock time that gets worse than linear, and memory usage that trends upward across a run without an actual reference leak.

### What I checked and ruled out

- `actor_loss` / `value_loss` appended into `trainer.logs` (a `defaultdict(list)` that lives for the whole run and is returned in full at the end — `training_loop.py:186`): both are already reduced to plain Python floats via `.item()` before being stored (`td3.py`: `actor_loss = loss_vals_actor["loss_actor"].item()`, and similarly in `_update_critics`). No autograd graph or GPU tensor is retained there — ruled out as a cause.
- PPO (`ppo.py`) is **not** affected — it takes the `else` branch (`data["next", "step_count"].max()`, over just the current batch, not the whole buffer) because PPO is on-policy and doesn't set `_use_replay_buffer`.
- TD3, DDPG, SAC (`td3.py`, `ddpg.py`, `sac.py`) **are** all affected, since they all go through `TrainingLoop.run()` with `_use_replay_buffer=True`.

### The fix

Compute `max_length` from the batch that was just collected, not the whole buffer — it's already available, it's O(batch size) instead of O(buffer size), and it's precise enough for a log line:

```python
if trainer._use_replay_buffer:
    trainer.replay_buffer.extend(data)
    buffer_len = len(trainer.replay_buffer)
    max_length = data["next", "step_count"].max()
else:
    max_length = data["next", "step_count"].max()
    buffer_len = data.numel()
```

(This also means the `if`/`else` branches now compute `max_length` identically, so the branch could be collapsed further — but the minimal fix above is the one that removes the actual cost.)
