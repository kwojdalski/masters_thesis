### 1. (Most severe — new) `es_saturation_max_rate`/`es_stale_policy_min_ratio` guardrails are semantically broken for continuous-action algorithms (DDPG/TD3/SAC/continuous-PPO)

- `src/trading_rl/trainers/episode_stats.py:198-206`
```python

    long_pct = 100.0 * np.sum(arr > 0) / n_values
    short_pct = 100.0 * np.sum(arr < 0) / n_values
```

- `src/trading_rl/trainers/health_monitor.py:63-87`
```python
if self._stale_ratio > 0.0:
    if len(arr) > 1:
        changes = np.diff(arr, axis=0)
        changed_steps = (
            np.any(changes != 0, axis=tuple(range(1, changes.ndim)))
            if changes.ndim > 1
            else changes != 0
        )

    ...
```

What it computes vs. what it should: `pct_extreme` ("fraction of steps at full exposure") is defined as `arr != 0` (any nonzero value), and the stale-policy "changed" signal is `diff != 0` (any nonzero change). This is a correct proxy only for the discrete tri-state action encoding `{-1, 0, 1}` (short/hold/long), where nonzero really does mean "fully short or long." For continuous portfolio-weight actions (any `Bounded` action spec, e.g. TD3/DDPG/SAC/continuous-PPO on the `pooled_*` HFT-LOB configs visible in this repo's `thesis/qmd/results/`), action values are floats that essentially never land exactly on `0.0`. Concretely, an action of `0.003` (barely any exposure) is counted identically to `1.0` (full exposure) — `pct_extreme` will sit at ~1.0 almost every episode regardless of actual agent behavior, and the stale-policy `changed_steps` ratio will sit at ~1.0 too (any two floats differ) even if the agent's policy is actually converged/stable.

Concrete effect: with `es_saturation_max_rate` enabled (e.g. `0.9`) for a continuous-action run, the guardrail will fire almost immediately regardless of whether the agent is actually pinned at the position bounds, because `pct_extreme≈1.0` for virtually any nonzero continuous action. Conversely, `es_stale_policy_min_ratio` (meant to catch a policy that stopped changing) will essentially never fire for continuous algorithms, because tiny float noise between successive continuous actions is always nonzero — the exact opposite failure mode of a genuinely frozen policy would go undetected. Both are off by default (`0.0`), so this only bites when a user opts in for a continuous-backend run, but at that point the signal is meaningless/inverted relative to what the docstring promises ("Max mean extreme-position rate" / "not changing positions").

Proposed fix: gate the discrete-style exact-comparison logic on the action-space type (mirroring the `is_discrete = not isinstance(action_spec, Bounded)` guard already used in `episode_stats.extract_logged_actions`, `episode_stats.py:103`), and for continuous action spaces use a magnitude/threshold-based definition instead — e.g. `pct_extreme = mean(abs(arr) > extreme_threshold)` (where `extreme_threshold` is close to the action bound, not `0`) and `changed_steps = abs(diff) > change_epsilon` for the stale-policy ratio.

## 1. Random-baseline significance tests run against a pointwise cross-trial mean, not real sampled returns — deflates the "random" baseline's variance and biases every test toward "strategy beats random"

**File:** `src/trading_rl/evaluation/statistical_tests.py:148-168`

```python
random_returns_mean = np.mean(
    [t[:min_len] for t in random_baseline_trials], axis=0
)
random_strategy_returns = np.asarray(strategy_returns, dtype=float)[:min_len]
random_pair_mask = np.isfinite(random_strategy_returns) & np.isfinite(random_returns_mean)
...
random_results = run_statistical_tests(
    random_strategy_returns[random_pair_mask],
    random_returns_mean[random_pair_mask],
    BenchmarkName.RANDOM_ACTIONS,
    config,
)
```

`random_baseline_trials` is a list of `n_trials` (default ~100) *independent* random-policy return trajectories from `compute_random_baseline_returns` (`statistical_benchmarks.py:263-324`), called from `src/trading_rl/pipeline/evaluation.py:216-222` and fed straight through to `run_all_statistical_tests`. Instead of treating each trial as an independent observation, `random_returns_mean` averages **across trials at each timestep**, producing one smoothed pseudo-trajectory that is then passed as `baseline_returns` into `t_test`, `mann_whitney`, `permutation_test`, `sharpe_bootstrap`, and `sortino_bootstrap` (via `run_statistical_tests` → `TEST_REGISTRY`, `statistical_test_registry.py:242-474`).

Concrete example: with `n_trials=100`, a random policy draws `pos_i,t ~ Uniform(-1,1)` independently per trial, so `trial_i[t] = pos_i,t * price_ret_t`. A single trial has `std(trial_i[t]) ≈ 0.577 * |price_ret_t|`, but `mean_i(trial_i[t])` over 100 trials has `std ≈ 0.577 * |price_ret_t| / sqrt(100) ≈ 0.058 * |price_ret_t|` — the baseline series fed to every test has ~10x less volatility than any real random trader would ever experience, and its mean sits essentially at 0 at every step (since `E[pos]=0`). This artificially collapses the "random" Sharpe/Sortino denominators and the t-test/Mann-Whitney null variance, so almost any strategy will appear "significantly" better than random and its Sharpe/Sortino will appear to hugely outperform the random baseline — not because the strategy is good, but because the comparison group's variance was averaged away.

Notably, the codebase already has the statistically-correct pattern next to this bug: `summarize_random_baseline_trials` (`statistical_benchmarks.py:327-350`) computes a Sharpe **per trial** and then reports the mean/std *across trial-level Sharpes* — treating each trial as one independent draw, as it should. The `run_statistical_tests(... random_returns_mean ...)` call a few lines above ignores that pattern and manufactures a single denoised trajectory instead.

**Proposed fix:** Don't build `random_returns_mean` for use in per-step tests. Either (a) concatenate all trials into one flat empirical sample (`np.concatenate([t[:min_len] for t in random_baseline_trials])`) so t-test/Mann-Whitney/bootstrap see genuine random-policy return draws with correct variance (note: strategy_returns would then need broadcasting/replication or a different comparison design since sample sizes differ), or (b) run the significance test at the trial-summary level (bootstrap the distribution of the ~100 trial-level Sharpes already computed by `summarize_random_baseline_trials` and test whether the strategy's single Sharpe falls outside that empirical distribution), consistent with how `summarize_random_baseline_trials` already treats trials as independent draws.

A related, lower-severity instance of the same pointwise-averaging pattern exists in `src/trading_rl/pipeline/evaluation.py:287-290` (`mean_returns = np.mean([t[:min_len] for t in random_trials], axis=0)`), but there it only feeds a single "Random" row into the benchmark **comparison table** (a point estimate), not a hypothesis test, so it's less severe — but worth aligning to the same fix for consistency.

## 2. `downside_deviation` metric is reported annualized, but `sortino_ratio` is computed from a different, non-annualized version of the same quantity that is never exposed

**File:** `src/trading_rl/evaluation/metrics.py:371-390`

```python
if _can_annualize:
    annual_vol = sigma * np.sqrt(periods_per_year)
    downside = np.minimum(r - rf_per_period, 0.0)
    downside_dev = np.sqrt(np.mean(np.square(downside))) * np.sqrt(periods_per_year)
    _MIN_ANNUAL_VOL = 1e-3
    if annual_vol >= _MIN_ANNUAL_VOL:
        _dd_raw = float(np.sqrt(np.mean(np.square(downside))))
        sharpe = sharpe_raw(mu - rf_per_period, sigma)
        sortino = sortino_raw(mu - rf_per_period, _dd_raw)
```

`downside_dev` (exposed to the report as `MetricReport.downside_deviation`, see `metrics.py:549`) is annualized (`× √periods_per_year`), but `sortino_ratio` is computed from `_dd_raw`, the **non**-annualized version — a value never written to any field. `metric_meta.py:151-156` explicitly documents `downside_deviation` as "used in the Sortino ratio denominator," which is false as coded.

Concrete example: `ppy=252`, `mu=0.0008`/bar, `_dd_raw=0.012` → `sortino_ratio = 0.0008/0.012 ≈ 0.067`, while the reported `downside_deviation = 0.012 * sqrt(252) ≈ 0.190`. Anyone (e.g. a thesis appendix cross-check script) recomputing `mean_return / downside_deviation` from the exported report gets `0.0008/0.190 ≈ 0.0042`, off from the reported `sortino_ratio` by a factor of `sqrt(252) ≈ 15.9`. This mirrors the existing `std_return`/`annualized_volatility` pattern (two separate, clearly-named fields) but `downside_deviation` has no non-annualized sibling field, so the description is simply wrong about which value backs `sortino_ratio`.

**Proposed fix:** Either add a `downside_deviation_annualized` field and keep `downside_deviation` as the raw per-bar value that actually matches `sortino_ratio`'s denominator (mirroring `std_return`/`annualized_volatility`), or fix the description in `metric_meta.py:151-156` to stop claiming equivalence with the Sortino denominator, and add a note that they differ by `√periods_per_year`.

**1. [State/silent-wrong-behavior] `RollingWindowScaler.transform()` propagates literal `+inf`/`-inf` into the observation vector, unlike its sibling scalers**
- File: `src/trading_rl/features/base.py`, lines 91–105 (class `RollingWindowScaler`, method `transform`)
```python
denom = np.sqrt(rolling_std**2 + self.epsilon)
normalized = (s - rolling_mean) / denom
...
# Fill NaNs from insufficient window (fewer than min_periods observations)
normalized = normalized.fillna(0.0)
return normalized.values if not isinstance(data, pd.Series) else normalized
```
- What it computes vs. what it should: `RunningMeanStd.transform()` (lines 220–229) and `TimeWeightedRunningMeanStd.transform()` (lines 407–414) both do `.fillna(0.0)` **and** `.replace([np.inf, -np.inf], 0.0)`. `RollingWindowScaler.transform()` only does `.fillna(0.0)` — it never guards against non-finite input. If a raw feature value at row `t` is `+inf` (e.g. any upstream division-by-near-zero, a corrupted tick, or one of several talib/ratio features that divide by `close`/`volume` without an epsilon guard), then `rolling_mean`/`rolling_std` computed from *prior* rows (they're `.shift(1)`'d, so they don't yet contain the inf) are finite, so `denom` is finite, and `normalized[t] = (inf - finite)/finite = +inf` — a literal infinity, not NaN, so `fillna(0.0)` does nothing.
- Concrete demonstration:
```python
s = pd.Series([1.0,2.0,3.0,4.0, np.inf, 5.0, 6.0])
rw = RollingWindowScaler(window=3, min_periods=1).fit(s)
rw.transform(s)
# -> [0.0, 0.0, 2.121108, 1.999900, inf, 2.121108, 2.121108]   <-- row 4 is +inf
```
  Compare `RunningMeanStd` on the same input: every value comes back finite (0.0 at the inf row).
- Downstream impact: `FeaturePipeline.transform()` (`src/trading_rl/features/pipeline.py` line 199, `result = result.dropna()`) does **not** remove `inf` rows (`pd.DataFrame({"a":[1.0, np.inf, 3.0]}).dropna()` keeps the inf row — verified). So any feature configured with `normalization_method: "rolling"` that ever produces a non-finite raw value will silently feed `+inf`/`-inf` straight into the RL agent's observation tensor, which will poison gradients / produce NaN losses without any error or warning (the opt-in `TRADING_RL_DEBUG_FEATURES=1` guard at lines 650–661 also won't catch it by default, and even when enabled it only logs a warning, it doesn't clip).
- Proposed fix: add the same `normalized = normalized.replace([np.inf, -np.inf], 0.0)` (or a documented clip strategy) after `.fillna(0.0)` in `RollingWindowScaler.transform()`, matching `RunningMeanStd`/`TimeWeightedRunningMeanStd`, and consider guarding the raw feature computations themselves at the source.

**2. [Silent-wrong-behavior / docstring mismatch] `safe_divide()` returns `NaN` instead of the documented `fill` value when the denominator is `NaN`**
- File: `src/trading_rl/features/lob_common.py`, lines 11–20
```python
def safe_divide(
    numerator: pd.Series,
    denominator: pd.Series,
    fill: float = 0.0,
) -> pd.Series:
    """Divide two Series, returning `fill` wherever denominator is zero."""
    result = pd.Series(fill, index=numerator.index, dtype=float)
    mask = denominator != 0
    result[mask] = numerator[mask] / denominator[mask]
    return result
```
- What it computes vs. should: the docstring promises `fill` for a zero denominator, but `mask = denominator != 0` evaluates `NaN != 0` as `True`, so any row with a `NaN` denominator is included in the "safe" branch and ends up as `numerator/NaN = NaN` in the output, not `fill`.
- Concrete demonstration:
```python
safe_divide(pd.Series([1.0, 2.0, 3.0]), pd.Series([0.0, np.nan, 5.0]), fill=0.0)
# -> [0.0, NaN, 0.6]   <-- row 1 should be 0.0 per the docstring, is NaN instead
```
- Used throughout `lob_book_features.py`/`lob_flow_features.py`/`lob_trade_features.py` (e.g. `BookPressureFeature`, `OrderBookImbalanceFeature`, `PriceVampFeature`'s `impact_price_side`) wherever a size/count column could be `NaN` (thin/short-depth book snapshots). In the current pipeline this is largely masked because `data/preparation.py` (lines 377, 1344) does a blanket `.dropna()` on the raw dataframe before feature computation, so `NaN` book columns rarely reach these features today — but the helper itself does not implement its documented contract, and any future caller or data source that leaves legitimate `NaN`s in size/count columns (rather than raising/dropping upstream) will get silent `NaN` propagation instead of the safe fallback.
- Proposed fix: `mask = denominator.notna() & (denominator != 0)` (or fill non-finite numerator/denominator combinations explicitly) so the function's behavior matches its docstring.

- **Mismatched-split substitution, unlabeled:** if a scenario's `results.json` has no `"test"` entry (e.g. an interrupted run, or `skip_final_eval`), the loop silently falls through to `"val"` then `"train"` and returns those numbers with no indication to the caller — which reports them into a table column/section explicitly labeled "test-split metrics" (e.g. `06-02-robustness-assessment.qmd` line 48: `tbl-cap: "H2 feature sensitivity: test-split metrics..."`). Train-split Sharpe/return figures (typically inflated by overfitting) could land in a table cell that claims to be test-split performance.
- **Mixing pooled and per-symbol metrics in one mean, category 1 (mixing pooled and per-trial statistics):** because `str.startswith` is used rather than an exact key match or a delimiter-aware check, once the fallback reaches `prefix="val"`, `entries` picks up **both** the single pooled `"val"` entry **and every** `"val__AAPL"`, `"val__MSFT"`, ... per-symbol entry (since `"val__AAPL".startswith("val")` is `True`). The subsequent `sum(vals) / len(vals)` then averages the pooled-portfolio Sharpe/Sortino/etc. together with each individual symbol's Sharpe/Sortino as if they were independent equal-weight samples of the same thing — an already-aggregated (pooled) statistic gets re-blended with its own disaggregated per-symbol components into one further mean, silently changing what the reported number represents.

Concrete example: pooled `"val"` Sharpe = 1.2 (computed over all six symbols jointly), and five `"val__<symbol>"` entries with Sharpe = 0.9, 1.0, 1.1, 0.8, 1.3. The current code reports `(1.2+0.9+1.0+1.1+0.8+1.3)/6 = 1.05`, double-counting the pooled figure's constituents and mislabeling the result as "test" Sharpe.

**Proposed fix:** (a) match split keys exactly or on a word boundary (e.g. `k == prefix or k.startswith(prefix + "__")` and treat the plain `prefix` entry and the `prefix + "__*"` per-symbol entries as two distinct groups, never averaged together in the same pass — or exclude per-symbol keys entirely from this aggregation, matching the intent of "aggregate the pooled split's own metrics"); (b) propagate which split was actually used to the caller (e.g. return `{"__source_split__": prefix, ...}`) so `load_scenario_metrics`/the QMD table can flag or refuse a val/train substitution instead of silently presenting it as "test".

### 8. `generate_upward_drift_pattern`: `pullback_floor` clamp silently deletes all volatility
`/Users/krzysztofwojdalski/github_projects/masters_thesis/src/data_generator/_drift.py:34-44`
```python
drift_curve = base_price * np.exp(drift_rate * steps)
noise = np.random.normal(0, volatility, n_samples)
close_prices = pd.Series(drift_curve * (1 + noise)).rolling(window=5, min_periods=1).mean().to_numpy()
floor = pullback_floor * np.maximum.accumulate(drift_curve)
close_prices = np.maximum(close_prices, floor)
```
The 5-bar trailing mean of an exponentially growing curve sits at `mean(exp(-r·k), k=0..4)` of the current level. For `drift_rate = 0.015` that is **0.9707 · drift_curve**, which is *below* the floor `0.995 · drift_curve`. So `np.maximum` replaces essentially every point with the floor. Measured (`upward_drift_strong.yaml`: drift_rate 0.015, vol 5e-4, floor 0.995):
```
fraction of points clamped to floor: 0.999
close == 0.995 * drift_curve exactly for i>=5: True
log-return std after clamp: 1.16e-15   mean: 0.015
```
`close` becomes a perfectly smooth deterministic exponential; the `volatility` parameter has **zero** effect. Any agent on this data faces a noiseless, perfectly predictable series (infinite Sharpe). The bug is order-dependent: the floor is meant to bound *drawdowns*, but is applied against the un-lagged `drift_curve` while `close` is a lagged average of it, so the lag alone trips the floor.
Bonus wrong-value: `upward_drift_strong.yaml` comments "Optimal return estimate: > 100%"; the actual total return over 500 steps is `exp(7.5)-1` ≈ **180 000 %** (and 1.6e11 at n=1000).
**Fix:** compare against the lagged reference, e.g. `floor = pullback_floor * np.maximum.accumulate(close_prices_unclamped)`, or apply the floor *before* the rolling mean.
Related: `upward_drift_large.yaml` comments "pullback_floor commented out for smoother trend" — omitting the key does **not** disable it; `_config.py:38` supplies `cfg.get("pullback_floor", 0.995)`.
